## 1. 카프카란?
- 카프카(Apache Kafka)는 고성능 분산 이벤트 스트리밍 플랫폼이다.
- 대규모 실시간 데이터 파이프라인, 로그 집계, 스트리밍 분석, 이벤트 소싱 등에서 표준처럼 사용된다.
- Pub-Sub 모델의 메시지 큐 형태로 동작하며 분산환경에 특화되어 있다.
### 1.1 메시지 큐(Message Queue)
메시지 지향 미들웨어(Message Oriented Middleware)는 비동기 메시지를 사용하는 각각의 응용프로그램 사이의 데이터 송수신을 의미하고, 이를 구현한 시스템을 메시지큐라 한다.

## 2. 카프카 특징
1. **높은 처리량과 낮은 지연시간 :** 카프카는 대용량 데이터를 실시간으로 처리할 수 있도록 설계되었다. 따라서 높은 TPS를 가지며, 실시간 데이터 스트림, 로그 집계, 이벤트 드리븐 아키텍처 구현에 적합하다.
2. **메시지 내구성 :** 카프카의 메시지는 메모리가 아닌 디스크에 영구적으로 저장된다. 예로 Redis Pub/Sub과 같은 경우 메시지가 디스크에 저장되지 않으며, 장애 발생 시 메시지는 유실된다. 반면 카프카는 기본적으로 모든 메시지를 디스크에 영구 저장한다.
3. **분산 아키텍처 :** 카프카는 카프카 클러스터 내부에 여러대의 브로커 서버를 구성하여 높은 `확장성`과 `내결함성`을 갖는다.
4. **Pull 기반 메시지 소비 :** 카프카는 컨슈머가 능동적으로 브로커로부터 메시지를 가져오는 Pull 방식을 취한다. 이로 인해 컨슈머는 처리 능력에 따라 메시지를 컨슘할 수 있기 때문에, 브로커로부터 압도당하지 않고 최적의 성능을 낼 수 있다.

## 3. 구성 요소
### 3.1 토픽
- 메시지가 저장되는 **논리적인 저장소**
- 데이터베이스의 테이블과 유사한 개념
- 여러 개의 파티션으로 구성됨

### 3.2 파티션
- 토픽을 여러 개로 나눈 **물리적인 저장 단위**
- 각 파티션은 순서가 보장된 메시지 시퀀스
- 병렬 처리와 확장성을 제공

### 3.3 오프셋
- 파티션 내에서 각 메시지의 **고유한 식별자**
- 순차적으로 증가하는 정수값
- 컨슈머가 메시지를 읽을 위치를 추적

### 3.4 메시지
- Kafka에서 전송되는 **데이터 단위**
- Key, Value, Timestamp, Headers로 구성
- 불변 특성을 가짐

## 4. 주요 컴포넌트
### 4.1 프로듀서
- 메시지를 토픽에 **발행**하는 애플리케이션
- 메시지를 어느 파티션에 보낼지 결정
- 배치 처리와 압축을 통해 성능 최적화

### 4.2 컨슈머
- 토픽으로부터 메시지를 **구독**하고 읽는 애플리케이션
- Pull 방식으로 메시지를 가져옴
- Consumer Group을 통해 확장성과 내결함성 제공

#### 4.2.1 Consumer Group
- 개념
  - 동일한 토픽을 구독하는 컨슈머들의 논리적 그룹
  - 각 파티션은 그룹 내 하나의 컨슈머만 할당
  - 로드 밸런싱과 내결함성 제공
- 리밸런싱
  - Consumer Group 의 가용성과 확장성을 확보해주는 개념
  - 컨슈머 추가/제거 시 파티션 재할당
  - 그룹 내 컨슈머 간 작업 분산
  - 일시적인 중단이 발생할 수 있음


### 4.3 브로커
- Kafka 서버 인스턴스
- 메시지를 저장하고 클라이언트 요청을 처리
- 여러 브로커가 클러스터를 구성

#### 4.3.1 클러스터
- 고가용성 (HA) 를 위해 여러 서버를 묶어 특정 서버의 장애를 극복할 수 있도록 구성
- Broker 가 증가할 수록 메시지 수신, 전달 처리량을 분산시킬 수 있으므로 확장에 유리

  > 동작중인 다른 Broker 에 영향 없이 확장이 가능하므로, 트래픽 양의 증가에 따른 브로커 증설이 손쉽게 가능

#### 4.3.2 Replication
- 데이터의 안정성과 가용성을 보장하기 위해 각 파티션의 데이터를 여러 브로커에 복사하여 저장하는 메커니즘
- 목적
  - **데이터 내구성**: 브로커 장애 시 데이터 손실 방지
  - **고가용성**: 서비스 중단 없이 장애 복구
  - **로드 분산**: 읽기 요청 분산
- 역할
  - 리더
    - 모든 읽기/쓰기 요청 처리
    - 프로듀서로부터 메시지 수신
    - 컨슈머에게 메시지 제공
    - 팔로워들과 데이터 동기화 관리
  - 팔로워
    - 리더로부터 데이터 복제
    - 리더 장애 시 새로운 리더 후보
    - 읽기 요청 처리 안 함 (기본 설정)

## 5. 데이터 흐름
1. Application → Kafka Producer
   - 애플리케이션이 생성한 키(key)·값(value) 레코드를 프로듀서가 수신해 전송 준비

2. Producer → Kafka Broker(Topic/Partition)
   - 프로듀서는 키 해시(Hash)로 파티션을 결정하고, 레코드를 디스크에 순차 Append

3. Kafka Broker
   - 브로커는 파티션 로그를 저장하며, 복제(Replication)로 고가용성을 확보

4. Broker → Consumer Group
   - 같은 Consumer Group 내 컨슈머 인스턴스들이 파티션을 분담해 pull 방식으로 레코드를 가져온다.

5. Offset Commit
   - 컨슈머가 처리(consume)를 완료하면 오프셋을 커밋해 재시작·장애 복구 시 정확히 이어서 처리하도록 한다.

## 6. Consumer Lag
프로듀서가 생산한 메시지와 컨슈머가 실제로 처리한 메시지 간의 차이를 나타내는 지표

### 6.1 중요한 이유
- **실시간성 지표**: 시스템의 실시간 처리 능력 측정
- **성능 모니터링**: 컨슈머 처리 성능 및 병목점 식별
- **스케일링 결정**: 컨슈머 인스턴스 증설 여부 판단
- **장애 감지**: 시스템 이상 상황 조기 발견
